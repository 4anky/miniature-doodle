# Правила git workflow Гитландии

Эти правила имитируют процесс в типичной продуктовой команде. CI (`tools/check.sh`) проверяет
большую часть из них автоматически.

## 1. Ветки

| Тип ветки       | Шаблон имени                   | Откуда создаётся | Куда вливается |
|-----------------|--------------------------------|------------------|----------------|
| Основная        | `main`                         | —                | —              |
| Задача квеста   | `quest/stage-<N>-<описание>`   | свежий `main`    | `main` через PR |
| Эксперимент     | `experiment/<описание>`        | свежий `main`    | никуда (не мёржится) |

- Имя ветки — латиница в нижнем регистре, слова через дефис.
- Перед созданием ветки всегда обновляй `main`:

  ```bash
  git switch main
  git pull --ff-only
  git switch -c quest/stage-1-village
  ```

- После мёржа PR удаляй ветку и локально, и на удалённом репозитории.

## 2. Коммиты

Формат — [Conventional Commits](https://www.conventionalcommits.org/ru/):

```
<тип>(<область>): <что сделано, в повелительном наклонении>

<необязательное тело: зачем и почему>
```

- **Типы:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.
- **Область** (необязательна) — локация мира: `village`, `forest`, `mountains`, `castle`,
  `dragon-lair`, `inventory`.
- Заголовок — не длиннее 72 символов, без точки в конце.
- Один коммит — одно логическое изменение. Не смешивай «починил опечатку» и «добавил героя».

Примеры:

```
fix(village): исправить опечатки на доске объявлений
feat(village): записать героя в книгу деревни
chore(forest): убрать проклятый гриб
```

## 3. Pull Request

- Целевая ветка — `main`.
- Заголовок PR — в том же формате, что и коммит.
- Заполни шаблон описания (он подставится автоматически) и отметь чекбоксы.
- Мёржить можно только при зелёной проверке `quest-check`.
- Не пушь merge-коммиты из `main` в свою ветку — актуализируй ветку через `git rebase origin/main`.
- После `rebase` пушь только через `git push --force-with-lease` (никогда не голый `--force`).

## 4. Стратегия слияния

| Ситуация                                         | Кнопка в GitHub        |
|--------------------------------------------------|------------------------|
| Несколько осмысленных коммитов, важна история    | *Rebase and merge*     |
| Один аккуратный коммит                           | *Rebase and merge* или *Squash and merge* |
| Много «грязных» WIP-коммитов (так делать не надо) | *Squash and merge*     |

На этапе 2 используй **Rebase and merge** — три коммита должны попасть в `main` как есть.

## 5. Релизы

- Релиз помечается **аннотированным** тегом `vMAJOR.MINOR.PATCH` на коммите в `main`.
- Тег пушится явно: `git push origin v1.0.0`.
