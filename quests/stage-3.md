# Этап 3. Рунные врата

**Навыки:** параллельная работа в двух ветках, конфликт слияния, `rebase`,
`push --force-with-lease`.
**Ветки:** `quest/stage-3-fire` и `quest/stage-3-ice`

## Легенда

Прочитай `world/mountains/rune-gate.md`. Ты будешь играть за обоих магов — как два
разработчика, которые одновременно правят одну и ту же строку.

## Задание

**Важно соблюдать порядок шагов** — иначе конфликт не возникнет.

1. Обнови `main`. Создай от него ветку `quest/stage-3-fire`.
   Замени `RUNE: ????` на `RUNE: огонь`. Коммит, push, открой PR. **Пока не мёржь.**
2. Вернись на `main` (тот же, не обновлённый). Создай от него ветку `quest/stage-3-ice`.
   Замени `RUNE: ????` на `RUNE: лёд`. Коммит, push, открой второй PR. **Не мёржь.**
3. Смёржи PR огненного мага. Посмотри на PR ледяного мага — GitHub сообщит о конфликте.
4. Разреши конфликт локально **через rebase**, а не через merge:

   ```bash
   git switch quest/stage-3-ice
   git fetch origin
   git rebase origin/main
   # конфликт в rune-gate.md — объедини руны по правилу из файла
   git add world/mountains/rune-gate.md
   git rebase --continue
   ```

   Итоговая строка: `RUNE: огонь+лёд`. Маркеров `<<<<<<<`, `=======`, `>>>>>>>` в файле
   остаться не должно.
5. `tools/check.sh` — проверка убедится, что ветка стоит поверх свежего `main`.
6. Обычный `git push` будет отклонён — история ветки переписана. Используй
   `git push --force-with-lease`.
7. Убедись, что конфликт в PR исчез и проверка зелёная. Смёржи.

## Вопросы для самопроверки

- Чем `--force-with-lease` безопаснее, чем `--force`?
- Почему после rebase у твоего коммита новый SHA?
- Что было бы в истории, если бы ты сделал `git merge origin/main` вместо rebase?

## Критерии прохождения

- `quest/stage-3-fire`: в файле `RUNE: огонь`;
- `quest/stage-3-ice`: в файле `RUNE: огонь+лёд`, ветка основана на актуальном `main`,
  merge-коммитов в ветке нет;
- маркеров конфликта нет нигде в `world/`.
